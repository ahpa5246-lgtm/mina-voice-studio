# الأسئلة المتكررة وقوائم فحص الإطلاق

## ما الذي أفعله إذا لدي 0 نجوم؟
هذا الرقم ليس حكمًا على الجودة. راجعي أن المستودع وصفه واضح وTopics مضبوطة وصور حقيقية وروابط وأوامر التثبيت تعمل. اختبري مقطعًا قابلًا للتجربة. تحدثي مع 3 مستخدمين حقيقيين وحوّلي مشاكلهم إلى Issues قبل حملة أكبر.

## هل أقول للمساهمين: اعملوا على مشروعي مقابل أن تعطوني نجمة؟
لا. هذا يضر مصداقية الاستوديو. يمكنك القول: "If you found this useful, a star helps discoverability" خارج الأماكن التي تمنع استجداء الأصوات، ودون مكافأة أو شرط أو تجميع جماعي. على HN وProduct Hunt لا تطلبي التصويت.

## ماذا لو Fork شخص المشروع ووضع اسمه؟
MIT يسمح بنسخ المشروع وتعديله والتوزيع وفق شروطه، بما فيها حفظ إشعارات الحقوق والترخيص. لا تقدمي بلاغًا كيديًا لأن Fork مسموح. ميّزي المستودع الأصلي وتاريخ التأسيس، واحتفظي بتاريخ Git. يمكن الاستشارة قانونيًا عند وجود خرق فعلي للترخيص أو انتحال علامة.

## هل على GitHub أن يحفظ الفكرة باسمي لمجرد وجود CODEOWNERS؟
لا. CODEOWNERS خاص بمراجعة الملفات ولا يمنح براءة أو احتكار الفكرة. يوثق AUTHORS وGOVERNANCE دور المؤسسة الأصلي؛ يحتفظ كل طرف بحقوقه وفق الرخصة والقانون.

## هل يجوز نشر صور الواجهة والملفات الصوتية من Kaggle؟
الصور الحقيقية في docs/assets/screenshots مناسبة للعرض العام إذا لم تحتوِ بيانات خاصة. أي ملف صوت: راجعي رخصته وشروط النموذج وحقوق عينة المرجع؛ لا تنشري نسخ أصوات أشخاص دون إذن. سجلي النموذج وتاريخ التوليد وhash حين تنشرين عينة تقييم.

## هل أحتاج Discord Server؟
ليس في البداية. GitHub Discussions وIssues يكفيان عندما يكون المجتمع صغيرًا؛ Discord قد يقسم المعرفة إلى رسائل يصعب البحث عنها. افتحي سيرفر فقط إذا أصبحت هناك أسئلة متكررة تحتاج لقاءات، واصنعي قناة Linking Back إلى Issues للقرارات الرسمية.

## هل أنشر في كل المنصات في اليوم ذاته؟
لا. اختاري 1–2 جمهور مناسب كل أسبوع بنص أصلي يخدمهم، مع قراءة القواعد والرد على التعليقات. إعادة نشر محتوى نفسه بكثافة Spam حتى لو كان المستودع مجانيًا.

## كيف أرتب أول 8 مهام؟
2 توثيق + 2 اختبارات + 1 وصولية + 1 API + 1 GPU بحثية (بعد موافقة وتجهيز البيانات) + 1 إصلاح تجربة استخدام. أنشئيها فقط بعد التحقق أن المشكلة لا تزال موجودة.

## كيف أتعامل مع طلب يتطلب GPU ولا أملكه حاليًا؟
لا تعدي بإكماله. قسميه إلى Task إعداد Benchmark وTask تنفيذ فعلي منفصل. أي قياس يجب أن يذكر GPU، إصدار نموذج، بيانات اختبار مرخصة، وعينة WAV أصلية مع بصمة تحقق.

## كيف أفتح بوابة مساهمات ضخمة بدون فقد التحكم؟
- CODEOWNERS مع قواعد Review فعالة.
- CONTRIBUTING واختبارات CI.
- Issues ذات معيار قبول.
- Fork/PR بدل منح write لكل مساهم.
- Governance يوضح دور Mina وحقوق الجميع.
- تسمية المشروع الأصلية ومصدره واضحة بلا مبالغة.
- إصدارات وشكر أصحاب المساهمات.

## ماذا بعد أسبوع بلا ردود؟
انظري إلى نقاط الاحتكاك: نصب نموذج ثقيل؟ لا يوجد Demo؟ ماذا يحتاج الزائر أن يفعل أولًا؟ اجعلي أول نجاح خلال دقائق على مستوى الواجهة، ثم وضحي المطلوب للنموذج. حسني README وIssue بدل شراء تفاعل.

## قائمة فحص قبل عرض إعلامي كبير
- [ ] تجربة مستخدم خارج الفريق ناجحة ويمكن عرضها.
- [ ] Demo منشور فقط عند التحقق من الحماية والترخيص.
- [ ] لا مقارنة غير مثبتة مع ElevenLabs أو DAW.
- [ ] المساهمون لديهم 5 مهام قابلة للعمل.
- [ ] Releases وREADME صحيحان.
- [ ] فيديو وتعليق صوتي وموسيقى مرخصة.
- [ ] ليس هناك سر KAGGLE أو بيانات شخصية في الصور/السجلات.
- [ ] رسالة التأسيس واضحة مع حفظ أسماء المساهمين.
- [ ] لا استجداء تصويت في Product Hunt/Hacker News.
- [ ] وقت للرد على التعليقات والدعم.

## قالب تعيين عملية لمدة أسبوعين
**Day 1:** اطلبي خطة من المساهم.
**Day 2–3:** قدمي مصدرًا أو اختبارًا موجودًا إذا تعثر.
**Day 4–7:** تحديث حالة علني (بدون مطالبة مبالغ بها).
**Day 8–14:** استلام PR أو تقسيم المهمة؛ إن لم توجد استجابة، تحققي من رغبة المساهم قبل إعادة فتحها.
**بعد الدمج:** Release note شكر وموجز تقني.

## قائمة فحص شهرية للمؤسسة
- [ ] تأكدت من 2FA وصلاحيات الوصول.
- [ ] راجعت متغيرات Actions السرية دون طباعتها.
- [ ] راجعت دقة License/README/Founder credit.
- [ ] وثقت 3 مشاكل حقيقية حُلت بالمشروع.
- [ ] حدثت 5 Issues لـ Good First Issue.
- [ ] شكرتُ أصحاب مساهمات خارجية مكتملة.
- [ ] قيمتُ القنوات الناجحة بناء على مستخدمين حقيقيين.
- [ ] أوقفتُ محتوى قديمًا يصف ميزات لم تتأكد بعد.
