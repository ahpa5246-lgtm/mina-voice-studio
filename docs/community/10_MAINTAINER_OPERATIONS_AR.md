# دليل الإدارة اليومية للمؤسسة ومشرفي المجتمع

## مسؤوليات أسبوعية
1. **الاثنين:** اقرئي Issues الجديدة؛ اطلبي خطوات إعادة إنتاج دقيقة أو انقلي الفكرة إلى Discussion.
2. **الثلاثاء:** راجعي أول PR من مبتدئ، وأجيبي بتعليق تعليمي محدد.
3. **الأربعاء:** اختبري واحدًا من مسارات المنتج من منظور أول مستخدم.
4. **الخميس:** حدّثي قائمة Good First Issues، وأغلقي المكرر مع روابط واضحة.
5. **الجمعة:** شاركي تقدمًا تقنيًا مثبتًا وأسماء أصحاب المساهمات.
6. **بقية الأيام:** عندما يسمح الوقت، ردي على أسئلة المجتمع ولا تتعهدي بساعات خدمة دعم لا تستطيعين الالتزام بها.

## تصنيف القضايا
- **Bug:** يصف سلوكًا مخالفًا مع خطوات وبيئة تشغيل ونتيجة متوقعة.
- **Feature idea:** سؤال مفتوح، يذهب إلى Discussions قبل تقسيمه.
- **Contributable task:** قرار نطاقه واضح، مع Tests/Acceptance.
- **Security:** لا تطلبي كشف ثغرة في العلن؛ اقرئي SECURITY.
- **License/privacy:** يحتاج تحققًا قبل قبول كود/أصوات.
- **User help:** سؤال دعم وليس Issue تطوير ما لم يؤكد bug.

## أسلوب مراجعة يحفّز المساهمة
الخطأ: "الكود سيئ اعده". البديل: "في حالة غياب النموذج، الدالة تعيد success مع ملف غير موجود. يرجى جعلها تعيد 503 مع اختبار يغطي الحالة في tests/test_...".
الخطأ: دمج PR غير مختبَر لإسعاد المساهم. البديل: اشكري الجهد، اطلبي اختبارًا محددًا، وضحي معيار القبول.
الخطأ: تجاهل PR ثلاثين يومًا دون إشعار. البديل: تعليق معلن يشرح أن الوقت الحالي لا يسمح، مع إعطاء خيار نقل المهمة إلى مساهم آخر.
الخطأ: توجيه المساهم لترقية المكتبة لمجرد أنها أحدث. البديل: اختبري التوافق مع checkpoint وأوزانها، وحددي سبب الترقية.
الخطأ: حذف حقوق نسب المؤلفين الأصليين. البديل: إشعارات تراخيص ومصدر المشروع الأصلي والتزام LICENSE.

## إيقاع المراجعة
- ابدأي بحل المشاكل ذات الأولوية P0 التي تمنع تثبيت الواجهة أو تنتج نتائج زائفة.
- لا تراجعي بناء Timeline ضخم قبل الاتفاق على مواصفات minimal.
- اجعلي كل PR صغيرة ما أمكن؛ PRs الضخمة تُقسم إلى تغييرات أصغر إلا إذا كان السبب التقني يبرر.
- الشكر العلني فقط عندما يسمح المساهم بذكر حسابه؛ الأسماء الظاهرة في GitHub عامة أصلًا.
- عندما تردين استخدمي لغة واضحة؛ يمكن الرد بالعربية أو الإنجليزية.
- اختبار GPU مكلف: لا تشغليه على PRs غير موثوقة تلقائيًا، واختبري بإذن وتكلفة معلومة.

## نموذج Release Notes شهري
**What shipped:** المزايا المدعومة بروابط PR.
**Testing:** Python/Chromium + GPU إن شُغّل فعليًا مع أسماء الأجهزة.
**Known limitations:** ما لم يُختبر بعد.
**Contributors:** الأشخاص الذين ساهموا كود/توثيق/اختبارات.
**Breaking changes:** تفاصيل تثبيت وعملية رجوع.
**Next focus:** ثلاث Issues مفتوحة بدل 100 وعد.

## إدارة الخلافات
1. اسمعي المقترح وافصلي الرأي عن الشخص.
2. قدمي معيارًا هندسيًا قابلًا للاختبار.
3. إذا كان خلافًا حول المنتج لا bug، انقليه إلى نقاش عام.
4. اشكري المساهم حتى لو رفضتِ تغييره.
5. استخدمي قواعد السلوك للتهديد أو التحرش، مع الحد الأدنى من التعرض العام للبيانات الخاصة.

## كيف نمنع النجوم الوهمية والشعارات المضللة؟
لا نصوص "Star for Star"، ولا Bot accounts، ولا جوائز/تذاكر مقابل stars أو upvotes، ولا مساهمات تُطلب فقط لتحسين عدّاد GitHub. استخدمي CTA حياديًا: "Try it; if useful you can star it, report an issue, or contribute" في README حيث تسمح سياسة المكان. لا تطلبي التصويت على Hacker News أو Product Hunt، ولا تنشري محتوى مولدًا آليًا حرفيًا في HN.

## لو اختفيتِ عن المستودع لبعض الوقت
اتركي Status في Discussions/README: آخر إصدار، المشاكل الحساسة، حدود الدعم، الملفات القابلة للتجربة، خطوات المشاركة. لا تعطي أحدًا كلمة مرور الحساب أو مفاتيح Kaggle. إذا أصبحت هناك مجموعة Maintainers موثوقة، وثقي أدوارهم مع احترام قيادة المؤسسة وحقوقهم.
