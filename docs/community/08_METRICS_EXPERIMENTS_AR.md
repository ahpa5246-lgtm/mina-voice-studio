# كيف نعرف إن كان الانتشار حقيقيًا؟ المقاييس والتجارب

## مشكلة القياس
عدد GitHub Stars يعبر عن اهتمام؛ لا يعني عدد التثبيتات أو جودة TTS. تنزيل GitHub release لا يعني نجاح التشغيل. Fork قد يكون للتعلم وليس مساهمة. لا تقيسي جميع القنوات بعدد مشاهدات فقط.

## حساب معدلات مفيدة
- **Star growth/week** = Stars في نهاية الأسبوع - Stars في بدايته.
- **Issue resolution rate** = القضايا المحلولة خلال الفترة / القضايا المعالَجة القابلة للحل خلال الفترة × 100؛ عرّفي البسط والمقام.
- **PR merge rate** = PRs المدمجة / PRs القابلة للمراجعة خلال الفترة × 100. لا تحسبي PRs مفتوحة للتو فاشلة.
- **First response time** = زمن أول رد ذي معنى من maintainer، لا رد bot آلي فقط.
- **Time-to-first-working-WAV** = زمن من إكمال التثبيت إلى إنتاج ملف WAV سليم على جهاز محدد عند توفر المحرك.
- **Docs-to-issue** و **issue-to-PR** = التحويل في القناة التي تملك بياناتها، لا تفترضي زيارات لا تستطيعين قياسها.
- **Retention** = كم مستخدمًا عاد لتجربة ثانية خلال شهر، بناء على استطلاع اختياري من مستخدمين وافقوا، لا تتبعيهم خفية.

## الحد الأدنى لجمع البيانات باحترام الخصوصية
- GitHub Insights وStars/Forks/Issues/PRs عامة ومناسبة للقياس.
- روابط UTM اختيارية قد تساعد في موقع خارجي تملكينه إن كان يطبق سياسة خصوصية؛ GitHub لا يعطيك تلقائيًا تحليلات مفصلة لكل زائر.
- استبيان اختياري قصير في Discussions: نظام التشغيل، هل نجح التثبيت؟ أي محرك؟ ما أول خطأ؟ **لا تطلبي صوت المستخدم أو عنوانه الدقيق أو مفاتيحه**.
- نتائج Kaggle: checkpoint، hardware، latency، WAV hashes، WER/CER على عينات معروفة؛ صوت الأداء والعواطف يحتاج تقييم استماع منفصل.
- أسماء المساهمين علنية في GitHub؛ لا تجمعي ملفات شخصية إضافية بلا داعٍ.

## تجربة عنوان/صورة واحدة في كل مرة
1. اكتبي فرضية: "وصف واضح لصناعة حوار الكرتون قد يجذب مستخدمًا أنسب من شعار AI Voice".
2. اختاري متغيرًا واحدًا: عنوان مقال أو Thumbnail، وليس كل شيء دفعة واحدة.
3. حددي أسبوعين للمقارنة دون تكرار المنشور المخالف لقواعد المنصة.
4. تابعي زيارات قابلة للقياس/ملاحظات الجمهور وIssues الموثقة، لا تعتبري نجوم الأسبوع نتيجة سببية مؤكدة إن نشرت في قنوات متعددة.
5. إن زاد التفاعل الحقيقي من دون زيادة Stars، قد يكون جمهور المنصة غير مستعد للتنزيل؛ حسني الدليل أو demo.

## أهداف مرنة وأرقام إنذار
- إذا 100 زيارة مرصودة وأقل من مستخدم واحد يثبت الواجهة: راجعي الخطوات والحد الأدنى للمتطلبات.
- إذا PRs كثيرة لكنها تفشل CI: اطلبي مهامًا أصغر واختبارات توضيحية.
- إذا Issue لا تملك معيار قبول: أعيدي كتابتها قبل طلب متطوع.
- إذا ظهرت شكوى خصوصية أو ترخيص: أوقفي نشر العينات المتأثرة حتى المراجعة.
- إذا نسخ المحتوى إلى منتج آخر تحت MIT مع الإشعار الصحيح: التركيز على تميز مشروع Mina وتجربة المستخدم وتوثيق تاريخ التأسيس؛ ليس استخدام بلاغات حقوق غير صحيحة.
